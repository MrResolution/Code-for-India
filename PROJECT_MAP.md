# 🗺️ Project Map

One page to find your way around this repository: what is where, how the pieces talk to each other, and what to watch out for. If you move or add something, update this file in the same change (see [AGENTS.md](AGENTS.md)).

**At a glance**
- **Robots:** 🦾 Arm (5 servos + geared gripper), 🤖 Quard Bot (8-servo quadruped), 🚀 Rover (sensor node), 🐕 Dogu (12-joint quadruped, model only).
- **Two dashboards:**
  - A desktop PyQt5 app with RViz2 embedded.
  - A browser dashboard with a Three.js twin.
- **Target platform:** Ubuntu 24.04 + ROS 2 Jazzy. Both dashboards also run "UI only" without ROS, which is how UI work is done on Windows or macOS.

## 4. How the pieces talk

```text
 Desktop app (calibrated_joint_gui.py) ──/joint_states (arm + Quard + Dogu)──► robot_state_publisher ──► RViz2 (docked)
   │  sets /robot_state_publisher robot_description on tab change (RViz follows the tab)
   │  /servo_calibration  (CALIB:… , RAW:<line>, LINK:<cmd>)
   ▼
 servo_serial_commander ── USB serial or UDP :8888 ──► Arm ESP32
   │  /esp32_link_state (JSON, transient-local)  /esp32_console  /esp32_connection_status
   └────────────────────────────────────────────► desktop app + web server (link cards, consoles)

 Browser ◄── HTTP :8000 ──► web_dashboard/server.py ──(rclpy if available)──► same topics as the desktop app
 Desktop app / server.py ── HTTP ──► Quard Bot ESP32      Desktop app / server.py ── HTTP /data or serial ──► Rover
```

| Topic | Type | Published by | Read by |
|---|---|---|---|
| `/joint_states` | `sensor_msgs/JointState` | desktop app, web server, `servo_simulator`, `arm_simulator.py`, `servo_serial_publisher`, `gesture_teleop_node` | `robot_state_publisher`, `servo_serial_commander`, `unified_robot_commander`, desktop app (gesture mirroring) |
| `/servo_calibration` | `std_msgs/String` | desktop app, web server | `servo_serial_commander`, `unified_robot_commander` |
| `/esp32_link_state` | `String` (JSON, latched) | `servo_serial_commander` | desktop app, web server |
| `/esp32_console` | `String` | `servo_serial_commander` | desktop app, web server |
| `/esp32_connection_status` | `String` | `servo_serial_commander`, `unified_robot_commander` | desktop app, web server |
| `/fleet/cmd`, `/fleet/status`, `/fleet/telemetry` | `String` | `unified_robot_commander` (it subscribes to `/fleet/cmd`) | any |

ROS entry points (`ros2 run servo_joint_publisher <name>`) are `calibrated_joint_gui`, `servo_serial_commander`, `servo_serial_publisher`, `servo_simulator`, `gesture_teleop_node`, `unified_robot_commander` and `web_dashboard`.

`servo_serial_commander` parameters are `use_wifi` (False), `esp32_ip`, `udp_port` (8888), `port` (`/dev/ttyUSB0`), `baudrate` (115200) and `max_cmd_rate` (50).

## 8. Pitfalls (read before changing things)

1. **Repo-root detection.** Both apps find the repo by walking up to a folder that holds `servo_calibration.json` **and** `urdf/` (or `$ROBOT_PROJECT_DIR`). Never move or rename either.
2. **Absolute mesh paths.** URDFs contain `file:///home/sabo/Documents/learn_/Hardware/...`.
   - `display_ros2.launch.py` rewrites that prefix to the real repo path.
   - The `/home/sabo` launchers do not: `launch_gesture_teleop.sh`, `launch_quard_rviz.sh` and `urdf/unnamed/*.sh`.
   - Keep the prefix when generating URDFs (`build_dogu.py --mesh-prefix`).
3. **Mesh lookup is by file name.**
   - The web server searches four folders in a fixed order (§5): `arm`, `quard_bot`, `unnamed`, `dogu`. The first match wins.
   - `urdf/unnamed/meshes/stl/` already repeats many arm and Quard names.
   - Give new meshes a robot prefix (as `dogu_*.stl` does), or the twin may load another robot's file.
4. **`urdf/unnamed/` is load-bearing.**
   - Despite the name, it holds the launch file every RViz launcher uses.
   - Its `unnamed.urdf` is no longer the arm: upstream commit `7944d8d` replaced it with Dogu's raw Phobos export.
   - Gesture teleop uses `unnamed_gazebo.urdf`.
5. **One owner for the arm serial port.** Only `servo_serial_commander` opens it. Dashboards reach the arm through ROS topics (`RAW:` and `LINK:` on `/servo_calibration`).
6. **E-STOP is software only.** Any new motion feature must stop in `engage_estop()` (desktop) or `engageEstop()` (web), and refuse to start while engaged. Dogu's tab is the smallest example.
7. **No fake data.** Readings show `--` or "No data" until a device replies. Simulators must be clearly labelled (the arm's Start Sim, `servo_simulator`).
8. **Line endings.** The repo stores LF.
   - On Windows, `core.autocrlf=true` would give shell scripts CRLF, and bash fails on `\r`.
   - `.gitattributes` forces `*.sh` to LF.
9. **Dogu is provisional.** It has no firmware, servo map or real limits, and its ±90° limits are placeholders. Its zero pose is *standing*, not the Blender layout.
10. **Rover transport mismatch.** The dashboards read HTTP `/data` or serial JSON, but `src/rover.cpp` has no HTTP handler: it reports over `robot_protocol.h` (UDP 8888). Check which firmware a rover actually runs before debugging the tab.
11. **Duplicate header.** `include/robot_protocol.h` and `lib/robot_protocol/robot_protocol.h` are identical. Change both, or consolidate after a test build.
12. **The web twin needs internet.** Three.js r128 and its loaders come from cdnjs and jsdelivr, as globals (`THREE.STLLoader`). Don't mix in ES-module builds.
13. **The arm calibration is live data.** `servo_calibration.json` drives real servo limits, so tests must work on a copy. Upstream raised every `servo_max_deg` to 180; check it against the hardware.
14. **Large binaries.** `cad/` holds about 140 MB, mostly `.blend` files. Avoid tools that read every file in the tree.
15. **The ROS launchers run the installed copy.**
    - `ros2 launch` and `ros2 run` start `servo_joint_publisher` from `ros2_ws/install`. After a plain `colcon build`, that is a copy that a `git pull` doesn't update.
    - `launch_dashboard.sh` and `launch_web_dashboard.sh` source `scripts/ensure_ros_build.sh`, which rebuilds the package when the copy differs from the checkout.
    - The web server and the no-ROS desktop path run straight from the checkout.
16. **One RViz, many models.** The desktop app swaps the model in `robot_state_publisher` as tabs change (`load_robot_description()`).
    - Every model must hang off `world`. `attach_to_world()` adds the link when a URDF starts elsewhere; it lives in both `calibrated_joint_gui.py` and `display_ros2.launch.py`, so change both.
    - Link names must stay unique across robots, like joint names: TF frames are global.
